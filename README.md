# mcp-documents

An **MCP (Model Context Protocol) server** that extracts clean text and Markdown from documents.

Built in **Rust** with a **Domain-Driven / Clean Architecture**, it extracts clean text/Markdown from **PDF (with OCR for scanned pages) plus MS Office and other formats** — Word, Excel, PowerPoint, RTF, EPUB, CSV.

## Features

- 📦 **Per-format tool surface** — each supported format (`pdf`, `doc`, `docx`, `rtf`, `xls`, `xlsx`, `ppt`, `pptx`, `csv`) exposes an `_info` tool (metadata) and an `_extract_markdown` tool (Markdown output), plus a single generic `classify_document` classifier. Output is always **Markdown**.
- 📄 **PDF extraction, per page** — text-based PDFs are converted to clean GitHub-Flavored Markdown via `pdf-inspector` (position-aware, real per-page text). Scanned/image pages are rendered and OCR'd.
- 🔍 **Real per-page PDF classification** — `pdf-inspector` classifies each page, so the PDF type is accurate: `TextBased`, `Scanned`, `ImageBased` or `Mixed`, along with the exact pages needing OCR.
- 🖼️ **OCR for scanned PDFs** — scanned/image-only **PDF** pages routed through a pluggable OCR provider (reference: **`tesseract-rs`** with **embedded tessdata** — English + Russian — no external process or system Tesseract). OCR is **real bounded page-parallel**, gated behind the `ocr-native` feature (default OFF). Non-PDF formats go straight through `anydoc` (no OCR).
- 🗂️ **Ranges** — per-format ranges select a subset: PDF `page_range`, doc/docx/rtf `word_range`, xls/xlsx `sheet`+`row_range`, ppt/pptx `slide_range` (`.ppt` whole-doc only), csv `row_range`.
- 🔌 **Pluggable architecture** — domain & application layers are decoupled from the MCP framework and the document libraries, making the OCR provider and even each extraction engine swappable.
- 📦 **Single self-contained binary** — zero runtime system dependencies; OCR (vendored Tesseract) and PDF rendering are embedded/static so nothing needs to be installed at runtime. (The binary dynamically links glibc/libstdc++ only.)
- 🧪 **Tested** — 95%+ line-coverage target on the default build (85%+ on the `ocr-native` build) enforced via `cargo llvm-cov` on a bare CI runner.

## How it works

The server is a **dual-mode binary** — a standalone CLI **and** an MCP stdio server — built with **Domain-Driven / Clean Architecture**: a `domain` layer defines the ports (traits) and value objects, an `application` layer implements the use cases, and an `infrastructure` layer provides the concrete adapters. The interface layer (built on `rmcp`) only talks to the application through those ports, so the OCR provider and even each extraction engine are swappable.

### The per-format pipeline

Every tool takes a source — a file **`path`** or base64 **`bytes`** — which is validated (size limit + `ALLOW_ROOT_DIR`) and read once. The pipeline then routes by **detected format** (from content, not the filename extension):

- **PDF** — a **per-page** pipeline. `pdf-inspector` classifies each page and extracts per-page native text. Pages with a text layer use that text directly; scanned/image-only pages are **rendered to a bitmap** (pure-Rust `pdf_render`) and **OCR'd** (via the `OcrProvider` port). Both are merged in page order, so a **Mixed** PDF interleaves text and OCR pages correctly, and a `page_range` (`page_from`/`page_to`) selects the pages to process. This is the **only** path that uses OCR.
- **CSV** — a **streaming** adapter (`csv` crate) reads the file row-by-row, so memory stays below file size. `csv_info` does a single pass (row count, column count, header); `csv_extract_markdown` skips to `row_from` and reads `row_to - row_from` rows into a Markdown table (O(range) memory). The header row is always shown.
- **xls / xlsx** — read by **`calamine`** (both `.xls` and `.xlsx`, distinguished by magic bytes). `*_info` lists the sheets (with row/col counts); `*_extract_markdown` renders a chosen `sheet` (default: first) as a Markdown table, restricted to `row_from`/`row_to`.
- **ppt / pptx** — **`.pptx`** (an OOXML zip) is parsed directly with `zip` + `quick-xml`: slides are separate `ppt/slides/slideN.xml` parts, so `pptx_info` reports a real slide count and `pptx_extract_markdown` honors a `slide_from`/`slide_to` range. **Legacy binary `.ppt`** has no separately-addressable slide parts, so it is routed through `anydoc` as a whole-document unit — `ppt_info` reports `slide_count: 1` and the slide range is ignored.
- **doc / docx / rtf** — word-processor formats have **no real page entity** (pagination happens at render time), so they expose **word and character counts** (`*_info`) and `word_from`/`word_to` word-range extraction via `anydoc`. A "word" is whitespace-delimited. A per-request `MAX_RETURN_CHARS` safety net caps the returned chunk size (guards against a single enormous "word").

Formats without a dedicated use case (ODF, EPUB) are still classified by `classify_document`; in the CLI they fall back to whole-document `anydoc` extraction.

| Concern | Library | Role |

OCR and PDF rendering happen **only** for scanned/mixed PDF pages — every other format goes straight through its dedicated adapter.

### OCR & tessdata

OCR is gated behind the **`ocr-native` cargo feature (default OFF)**. With the feature **off** the binary is pure-Rust and a stub `NoopOcrProvider` returns `OcrUnavailable` for scanned PDFs (never silent or partial output). The full self-contained OCR binary is built with the feature **on** — via **Docker multi-stage** or `make build`.

**Building with OCR (`ocr-native`):**

- Requires a **C++ compiler + CMake + internet** at build time (compiles the vendored Tesseract/Leptonica) and the env var **`TESSERACT_EMBED_LANGUAGES=eng,rus`**.
- **`rus.traineddata` must be pre-provisioned** before building: `tesseract-rs`'s `build.rs` only auto-downloads `eng`/`tur`, and `TESSERACT_EMBED_LANGUAGES` selects which **already-downloaded** files to embed — it does **not** download them. Embedding `rus` silently fails unless `rus.traineddata` is present in the tesseract-rs tessdata cache dir first. The `Dockerfile` and `make prepare-tessdata` fetch it from a mirror (`tessdata_best`) for you.

**Runtime startup (what the shipped binary does):**

- On startup the `TesseractOcrProvider` **materializes the embedded tessdata bytes into a stable per-user cache directory** — the bytes come from the binary, not disk/network, preserving the single-binary / zero-runtime-dependency property. The cache dir resolves in order:
  - `$XDG_CACHE_HOME/mcp-documents/tessdata`
  - `~/.cache/mcp-documents/tessdata`
  - a temp-dir fallback (`<tmp>/mcp-documents-tessdata`)
- It uses a **size-checked, self-healing fast path**: a `.traineddata` file is only (re)written when it is missing or its on-disk size differs from the embedded byte length; otherwise it is skipped with a cheap `stat`. Idempotent writes plus the size check mean **no lock is needed** (safe under concurrent starts/tests), and a torn write is repaired on the next startup.
- Tesseract is initialized **once** with `api.init(cache_dir, "eng+rus")` — the `init_embedded("eng+rus")` form does **not** work because the embedded map is keyed per single language. Each OCR call then **clones the initialized API via `try_clone()`**, so the ~0.5–1 s init cost is paid only once while enabling **page-parallel OCR**.

**OCR concurrency (real, bounded):** within a request, scanned pages are OCR'd **in parallel**, bounded by a semaphore sized to **`OCR_CONCURRENCY`** (default = CPU cores), and the number of OCR'd pages per request is capped by **`OCR_MAX_PAGES`** (default 300). Each page's render and OCR run through `tokio::task::spawn_blocking`, so the MCP server never stalls. Exceeding the page cap returns a `ResourceLimit` tool-level error.

## Quick Start

### Prerequisites

- Rust toolchain (stable) with `cargo`.
- **Local build (default features):** pure Rust — **no** C++ compiler / CMake / OCR data needed.
- **Full OCR build** (the shipped self-contained binary): needs a C++ compiler + CMake + internet at build time (to compile the vendored Tesseract+Leptonica and download `rus.traineddata`).
- **No runtime system packages required.** The server ships as a **single self-contained binary**: OCR runs on `tesseract-rs` with **embedded tessdata** (English + Russian) and PDF rendering is pure Rust. There is **no** runtime Tesseract, `libtesseract`/`libleptonica`, or `tessdata` to install — nothing is shelled out. (The binary dynamically links only glibc/libstdc++, so the Docker runtime image matches the builder's Debian ABI.)

### Build

The heavy OCR stack (`tesseract-rs`) is gated behind the **`ocr-native` cargo feature (default OFF)** so local dev stays pure-Rust. The full self-contained OCR binary is built via **Docker multi-stage**, which pre-provisions `rus.traineddata` and sets `TESSERACT_EMBED_LANGUAGES=eng,rus` (the default omits Russian).

```bash
# local dev — default features, pure Rust, no C++ toolchain
cargo build
cargo test

# full OCR binary — recommended (Docker multi-stage → self-contained)
docker build -t mcp-documents .

# full OCR binary — build locally with the wrapper
make build        # TESSERACT_EMBED_LANGUAGES=eng,rus cargo build --release --features ocr-native
```

> The default `cargo build` produces a working binary, but with the `ocr-native` feature **off** OCR returns `OcrUnavailable` for scanned PDFs. Build with `--features ocr-native` (or via `make build`/Docker) for full OCR support.

### Run as an MCP stdio server

```bash
cargo run --release
```

The server speaks MCP over **stdio** — launch it from your MCP client rather than a normal terminal. (Running the binary with no subcommand, or with `serve`, starts the MCP server.)

### Standalone CLI

The same binary doubles as a CLI for quick local testing (no MCP client needed):

```bash
mcp-documents classify <file>       # print classification (kind; for PDFs, PDF type + pages needing OCR)
mcp-documents extract <file>        # print extracted Markdown (any supported format)
mcp-documents serve                 # run the MCP stdio server (also the default)
```

## Available tools

The tool surface is **per-format**: one generic classifier plus, for each supported format, an `_info` tool (metadata as JSON) and an `_extract_markdown` tool (Markdown as text).

| Tool | Description |
|------|-------------|
| `classify_document` | Detect the kind of **any** supported document. For PDFs also returns the PDF type (`TextBased` / `Scanned` / `ImageBased` / `Mixed`) and the pages needing OCR. |
| `pdf_info` | PDF metadata: page count, PDF type, pages needing OCR. |
| `pdf_extract_markdown` | Extract a PDF as **Markdown** (OCR for scanned pages); optional `page_from`/`page_to` (0-based, end-exclusive). |
| `doc_info` / `doc_extract_markdown` | Word & char counts / extract a `.doc`; optional `word_from`/`word_to`. |
| `docx_info` / `docx_extract_markdown` | Word & char counts / extract a `.docx`; optional `word_from`/`word_to`. |
| `rtf_info` / `rtf_extract_markdown` | Word & char counts / extract an `.rtf`; optional `word_from`/`word_to`. |
| `xls_info` / `xls_extract_markdown` | List sheets / extract a `.xls` sheet as a Markdown table; optional `sheet` + `row_from`/`row_to`. |
| `xlsx_info` / `xlsx_extract_markdown` | List sheets / extract a `.xlsx` sheet as a Markdown table; optional `sheet` + `row_from`/`row_to`. |
| `ppt_info` / `ppt_extract_markdown` | Slide count / extract a `.ppt` (whole document; **no** slide range for legacy binary `.ppt`). |
| `pptx_info` / `pptx_extract_markdown` | Slide count / extract a `.pptx`; optional `slide_from`/`slide_to`. |
| `csv_info` / `csv_extract_markdown` | CSV metadata (rows, columns, header) / extract a CSV as a Markdown table (streaming); optional `row_from`/`row_to` over data rows (header always shown). |

**Common parameters:** every tool accepts a file **`path`** and optionally base64 **`bytes`** (used when the client passes the file content to the model; takes precedence over `path`). The `*_info` and `classify_document` tools return JSON; the `*_extract_markdown` tools return **Markdown only** — there are no plain-text tools. See [`SPEC.md`](./SPEC.md) §8.2 for details.

**Annotations:** every tool is **read-only** (it only reads/parses the given document and never modifies its environment) and is declared with explicit per-tool Annotations (`readOnlyHint: true`, `destructiveHint: false`, `idempotentHint: true`, `openWorldHint: false`) plus a human-readable `title` and per-tool usage guidance in its description. See [`SPEC.md`](./SPEC.md) §8.2 (M04).

### Using documents with MCP clients (e.g. opencode)

Text-only models cannot read PDF/binary attachments — opencode attaches the file on drag-and-drop / `[PDF]` reference, and the model rejects it (`this model does not support pdf input`). This is a **client-side** limitation (opencode issues #17205 / #42544; the fix is expected after v1.18.18). The reliable pattern is:

- Give the model the **file path** and have it call `classify_document` to detect the format, then the matching `<format>_info` / `<format>_extract_markdown` tool (e.g. `pdf_info`/`pdf_extract_markdown`, `xlsx_info`/`xlsx_extract_markdown`, `csv_info`/`csv_extract_markdown`).
- The tools also accept base64 `bytes` if the client hands the content to the model.

## Security / trust model

Read this before exposing the server beyond a trusted local MCP client.

- **Arbitrary file read by design.** The tools read **local file paths** (`path`). This server is intended to run on a machine the MCP client trusts — an untrusted MCP client (or one steered by untrusted prompt injection) can read any file the process user can read. This is an **arbitrary-file-read** boundary; treat the client as trusted.
- **`ALLOW_ROOT_DIR` restricts the read scope.** Every `path` is **canonicalized** (symlinks resolved; a leading `~` is expanded to your home directory) and must fall within `ALLOW_ROOT_DIR`. The default on Unix is **`~/Documents`** (falling back to `/` when the home directory is unavailable, e.g. in minimal containers) — the server reads your documents folder out of the box. Set `ALLOW_ROOT_DIR` to a specific directory to narrow (or `/` to widen) what can be read; paths outside it are rejected. The container image sets `ALLOW_ROOT_DIR=/data` (mount your documents there).
- **TOCTOU / symlink hardening.** Path files are **opened with `O_NOFOLLOW`** and `fstat`'d on the **same descriptor**, so a symlink or a file that changes between validation and read cannot redirect or race past the size check / root gate.
- **Input size cap.** `MAX_INPUT_BYTES` (default 250 MiB) caps the input size — enforced for paths (file size via `fstat`) and for `bytes` **before** base64 decode — so an oversized input becomes a `ResourceLimit` tool-level error rather than an OOM.
- **Decompression cap.** `MAX_DECOMPRESSED_BYTES` (default 256 MiB) caps each decompressed archive member (e.g. a PPTX slide part), guarding against zip/decompression bombs.
- **Bounded output.** `MAX_RETURN_CHARS` caps the returned chunk for **all** per-format extractors (doc/docx/rtf `word_range`, ppt/pptx, csv, xls/xlsx). `OCR_MAX_PAGES` caps the pages OCR'd per request and `OCR_CONCURRENCY` bounds OCR parallelism.
- **No shell-out / no external execution.** OCR and rendering run in-process with embedded data; nothing is shelled out.
- **Panic isolation.** Document parsing/conversion is wrapped in `catch_unwind`, so a malformed document becomes a tool-level error, never a crash.
- **Supply-chain guard.** The embedded `rus.traineddata` OCR model is verified against a pinned SHA-256 baked into the binary at startup; base container images and the model download are pinned by digest/checksum.

## Configuration (environment variables)

All settings have safe defaults and no framework prefix. They are read at call time.

| Env var | Default | Purpose |
|---------|---------|---------|
| `MAX_INPUT_BYTES` | `250 * 1024 * 1024` (250 MiB) | Hard cap on input size (path file size, or decoded base64 `bytes`). Enforced before read/decode. Exceeding → `ResourceLimit`. |
| `OCR_MAX_PAGES` | `300` | Per-request cap on the number of PDF pages that are OCR'd. Exceeding → `ResourceLimit`. |
| `OCR_CONCURRENCY` | CPU cores | Maximum PDF pages OCR'd **in parallel** per request (a semaphore). |
| `MAX_RETURN_CHARS` | `50_000_000` | Safety-net cap on the returned size of an extraction (doc/docx/rtf `word_range`, ppt/pptx, csv, xls/xlsx). Exceeding → `ResourceLimit`. |
| `MAX_DECOMPRESSED_BYTES` | `256 * 1024 * 1024` (256 MiB) | Cap on the decompressed size of a single archive member (e.g. a PPTX slide part) — guards against decompression bombs. Exceeding → `ResourceLimit`. |
| `ALLOW_ROOT_DIR` | `~/Documents` (Unix; `/` fallback if no home) | Every `path` is canonicalized (leading `~` expanded) and must be within this root; paths outside are rejected. The container image sets `ALLOW_ROOT_DIR=/data`. |
